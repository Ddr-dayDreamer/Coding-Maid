## MCP 接入说明

MCP 的本质：多给 LLM 发几条 `tools[]` 定义，执行时多一个路由分支。

当前架构：所有内置工具通过 `ToolRegistry` 统一注册，`ToolExecutor` 调 `registry.execute()` 执行，MCP 工具走独立路由 `mcpManager.executeMcpTool()`。`mcp-client.ts`(通信)、`mcp-manager.ts`(生命周期)、`executor.ts`(路由) 已有完整覆盖，无需大动。

## 技术实现要点

### 工具注册流程

加一个新工具需要两步：

1. **`src/tools/definitions/`** — 创建工具定义文件，导出 `ToolRegistration` 对象（含 name + schema + doc + handler 引用）
2. **`src/tools/index.ts`** — 在 barrel 文件加一行 `registry.register(xxxTool)`

> 如果需要 webview 也能感知到这个工具（例如在预设编辑器里显示），还需要在 `src/tools/builtin-tools.ts` 的 `BUILTIN_TOOLS` 数组加一行名字。这是 webview/extension 两个 bundle 依赖隔离的代价——webview 只能安全 import 纯数据文件。

定义文件通过 `ToolRegistration` 类型统一包含 schema、handler 引用和 doc 文档，`ToolRegistry` 自动生成 OpenAI function-calling 格式并注册路由。无需改动 `prompt.ts`、`executor.ts` 或 `templates/tools/`。`{{tool.xxx}}` 宏也自动从 registry 读取 doc 内容。


### LSP 工具实现参考

`get_errors`、`find_references`、`rename_symbol` 等工具可以通过 VS Code 的 `vscode.languages` API 或直接使用 Language Server Protocol 的请求/响应模式实现。Coding-Maid 作为 VS Code 扩展，可以直接调用 `vscode` 命名空间中的 API。

## 工具级审批预检器

### 设计动机

所有工具的审批流程默认一致（查 settings 模式 → 拦截/放行）。但某些工具需要**工具级特殊逻辑**：
- `bash`：预先检查命令是否包含 `rm -rf /` 等危险操作
- `write`/`edit`：检查是否修改系统关键文件
- 未来可能接入 AI 审批时，不同工具可能需要不同的预检策略

### 架构

```
checkApproval(toolName, rawArguments)
  │
  ├─ 1️⃣ 运行工具级 approvalChecker（如有定义）
  │     ├─ { action: "allow" }  → 直接放行，覆盖 settings 模式
  │     ├─ { action: "reject", reason } → 自动拒绝，告知 LLM 原因
  │     └─ { action: "require" } → 继续走 settings 模式检查
  │
  └─ 2️⃣ 查 settings 中的审批模式
        ├─ "none"    → 放行
        └─ "require" → 等待用户审批
```

### 相关文件

| 文件 | 说明 |
|------|------|
| `src/tools/types.ts` | `ToolApprovalCheckResult`（联合类型）、`ToolApprovalChecker`（签名） |
| `src/tools/registry.ts` | `ToolRegistration.approvalChecker?` 字段；`checkApproval()` 中调用 |
| `src/tools/approval-checkers.ts` | 各工具预检器实现（如 `bashApprovalChecker`） |

### 为工具添加预检器

三步即可：

```typescript
// 1. 在 approval-checkers.ts 中定义预检器
export const writeApprovalChecker: ToolApprovalChecker = (args) => {
  if (String(args.file_path ?? "").startsWith("/etc/")) {
    return { action: "reject", reason: "禁止修改系统配置文件" };
  }
  return { action: "require" };
};

// 2. 在工具定义中挂载
export const writeTool: ToolRegistration = {
  // ... 原有字段
  approvalChecker: writeApprovalChecker,
};

// 3. 完成，不需要改任何框架代码
```

### 预检器的三种返回

| 返回值 | 含义 | 使用场景 |
|--------|------|---------|
| `{ action: "allow" }` | 直接放行 | 安全只读命令跳过审批 |
| `{ action: "reject", reason }` | 自动拒绝 | 检测到危险操作，直接拦截 |
| `{ action: "require" }` | 走正常审批 | 拿不准，让用户决定 |

这三种返回与 settings 的两种模式（`none` / `require`）自由组合，覆盖所有场景。

### 当前已实现的预检器

#### Bash — `bashApprovalChecker`

自动拒绝的危险模式：

- `rm -rf /` — 递归删除根目录
- `mkfs` — 格式化磁盘
- `dd if=... of=/dev/sda` — 写入块设备
- `curl ... | bash` — 管道执行远程脚本
- Fork 炸弹、`chmod -R 000 /` 等

安全命令自动放行（暂禁用，等待测试体验后决定是否恢复）。

#### Write — `writeApprovalChecker`

自动拒绝的路径：

| 类别 | 示例 |
|------|------|
| Unix 系统路径 | `/etc/`, `/usr/`（不含 `/usr/local/`）, `/bin/`, `/boot/`, `/dev/` |
| macOS 系统路径 | `/System/`, `/Library/` |
| Windows 系统路径 | `C:\Windows\`, `C:\Program Files\` |
| 敏感配置文件 | `sudoers`, `passwd`, `shadow`, `hosts`, `fstab` |
| SSH/GPG 配置 | `.ssh/`, `.gnupg/`, `authorized_keys` |
| Shell 配置文件 | `.bashrc`, `.zshrc`, `.profile`（防持久化后门） |

#### Edit — `editApprovalChecker`

除与 Write 相同的路径保护外，额外检查：

- `replace_all: true` + `old_string` 长度 ≤ 2 → 自动拒绝（防止大范围意外替换）
- `replace_all: true` + `old_string` 为纯空白字符 → 自动拒绝
